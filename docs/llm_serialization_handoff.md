# 직렬화 LLM 트랙 — 1차 실측 근거 (DACON 완주 팀 경험 이관)

> **`dl_models.md` §빅테크 대형모델(LLM) 가중치 사용 검토의 결론(= LLM 트랙 제외)을 지지합니다.**
> 이 문서는 그 결론을 뒤집으려는 게 아니라, 근거를 **문헌 인용에서 1차 실측으로 격상**시키는 보강 자료입니다.
> 출처: 2026 AI·SW 디지털경진대회 AI부문(DACON Agent Action Decision Prediction) 팀 토큰강도 — 0.5B LLM 직렬화로 **완주·8위**한 팀의 실측치.

---

## 0. 한 줄 요약

DACON에서 직렬화 LLM으로 실제로 이겨본 팀의 데이터를 이 대회에 대입하면 — **시간 예산 3~4배 초과**이고, 설령 통과시켜도 **이 데이터는 LLM이 구조적으로 가장 못하는 유형**입니다. 트랙 제외가 맞습니다.

---

## 1. 시간 예산 — 추정치를 실측 앵커로 교체

**예산**: 245,789행 / 10분 = **행당 2.44ms**

**우리 실측 (DACON 최종 제출팩)**:

| 항목 | 값 |
|---|---|
| 모델 | HCX-0.5B (SequenceClassification, fp16) |
| GPU | T4 16GB |
| 처리량 | 30,000행 / **7분 15초** = **행당 14.5ms** |
| 토큰 | 중앙값 207 / p99 315 (max_length 384) |
| 환산 | 6.21M 토큰 / 435초 = **약 14.3k tok/s** |

**이 대회 대입** (L4는 T4 대비 fp16 처리량 약 2배 → ~27k tok/s 가정):

- 49컬럼 직렬화 시 행당 200~250토큰 → 245,789행 × 225 ≈ **5,500만 토큰**
- 5,500만 / 27k tok/s ≈ **34분** → 10분 한도의 **3.4배 초과**

> 📌 `dl_models.md`는 L4에서 0.5B를 15k tok/s로 잡아 54분으로 추정했습니다. 저희 T4 실측이 14.3k tok/s이므로 **그 추정치는 T4 수준으로 보수적**이고, L4 실제로는 34분 근처일 가능성이 높습니다. **다만 결론은 동일합니다 — 3배 이상 초과.** 팀 내 누가 다시 계산해도 같은 결론에 도달하도록 두 수치를 함께 남깁니다.

---

## 2. 어디까지 줄이면 들어가는가 (경계선)

들어가게 하려면 토큰 예산이 **600초 × 27k = 1,620만 토큰**이어야 합니다. 필요한 건 약 3.4배 축소:

| 구성 | 예상 시간 | 판정 |
|---|---|---|
| 0.5B + 225토큰 | ~34분 | ❌ 초과 |
| 0.5B + 64토큰(피처 압축) | ~10분 | ⚠️ 마지노선, 사고 위험 |
| **110M급 인코더 + 64토큰** | **~2분** | ✅ 물리적으로 통과 |

**즉 "LLM"을 포기하고 BERT-base/DistilBERT급 인코더로 내려오면 시간은 해결됩니다.** 그런데 그 지점에서는 이미 사전학습 언어지식이 거의 남지 않은 **그냥 작은 트랜스포머**이고, 그럴 거면 tabular 전용 구조(TabM·FT-Transformer)가 같은 파라미터 예산에서 더 낫습니다. **시간이 아니라 §3이 진짜 기각 사유입니다.**

---

## 3. 🔴 1차 증거 — 토크나이저는 수치 임계를 학습하지 못한다

`dl_models.md` 3번 항목("성능 근거 없음")은 문헌 근거인데, 저희는 **같은 실패를 실험으로 직접 겪었습니다.**

DACON 최종 발표 06 파트에 이렇게 실려 있습니다:

> **모델이 학습하지 못한 것은 숫자 크기 비교**
> 남은 예산이 5,000 미만이면 에이전트의 행동 방식 전환 → **토크나이저가 숫자를 조각으로 분할, 학습 불가**
> → **고정 규칙 12종으로 보정** (교차검증 10회 전부 통과, 누적 +0.0015~0.0029)

정리하면 — 0.5B LLM을 70만 행 규모로 파인튜닝하고도 **`budget < 5000`이라는 단일 임계 하나를 끝내 학습하지 못해서**, 사람이 짠 결정론적 규칙 12종으로 회수해야 했습니다. 토크나이저가 `5000`을 `50`+`00` 식으로 쪼개면서 수의 크기 관계가 파괴되기 때문입니다.

**그런데 이 대회 피처는 정확히 그 유형만 모여 있습니다:**

`balls_before` · `strikes_before` · `outs_before` · `inning` · `score_diff_home` · `score_diff_pitcher_team` · `run_total_before` · `num_runners_on` · `li` · `home_win_expectancy` …

전부 **수치 임계와 대소 비교로 결정되는 피처**입니다(볼카운트 2-1과 1-2는 완전히 다른 상황). 이건 GBDT의 분기 조건 그 자체이고, LLM이 가장 못하는 것만 골라 모은 셋입니다.

> **판정**: LLM 직렬화는 이 데이터에서 "잘 안 될 것 같다"가 아니라, **저희가 이미 실패를 확인하고 규칙으로 우회한 바로 그 실패 유형**입니다.

## 4. 그럼 DACON에선 왜 통했나 — 조건 판별 기준

같은 기법이 저기선 이기고 여기선 지는 이유가 분명합니다.

| 조건 | DACON (LLM 승) | 이 대회 |
|---|---|---|
| 입력 형태 | **자연어 요청문** ("이 모듈 어디서 쓰는지 다 찾아줘") + 파일 경로 | 수치/범주 코드 49컬럼 |
| 컬럼 타입 | 텍스트 중심 | int 26 · float 19 · object 4 (**object도 `top_bottom`·`base_state` 같은 코드형**) |
| 언어 사전학습 기여 | **직접 기여** (한국어 사전학습만으로 +0.0045 실측) | **0** — 이해할 언어가 없음 |
| 수치 임계 의존도 | 낮음 (`budget` 하나뿐 → 룰로 처리) | **전면적** |
| 결과 | 0.4358 → 0.7977 | — |

**판별 규칙**: 입력에 사람이 쓴 자연어가 있으면 LLM 직렬화를 검토하고, 없으면 검토하지 않는다. 이 대회는 후자입니다.

## 5. 그래도 트랜스포머가 값어치 있는 유일한 지점 — `trackman_history.csv`

179만 행 투구 로그는 **투수·타자 단위 시퀀스**라 진짜 순차 구조가 존재합니다. 여기엔 시퀀스 인코더가 의미 있을 수 있습니다. 단 형태가 다릅니다:

- ❌ "행을 직렬화해서 LLM에 넣기"
- ✅ "투구 이력 시퀀스를 인코딩 → **임베딩 벡터를 GBDT/TabM의 추가 피처로**"

**다만 우선순위는 낮습니다.** 최근 N구 구종 분포 · 평균 구속 · 회전수 롤링 통계 같은 **단순 집계 피처가 그 신호의 대부분을 1% 비용으로** 가져갑니다. 순서는 이렇습니다:

1. trackman 집계 피처(투수·타자 단위 요약)를 먼저 만들어 GBDT에 투입
2. 그 피처가 실제로 점수를 올리는지 확인
3. **올렸는데 더 짜낼 게 남았다고 판단될 때만** 시퀀스 인코더 검토

집계 피처가 무의미하면 시퀀스 인코더도 무의미할 확률이 높습니다 — 비싼 쪽을 먼저 시도할 이유가 없습니다.

## 6. 이 결론을 재검토할 트리거

다음 중 하나가 발생하면 다시 계산할 가치가 있습니다. 그 전엔 재론 금지(슬롯 낭비).

- 대회 규칙에 **자연어 텍스트 컬럼이 추가**되는 경우 (§4 판별 규칙 위반)
- 추론 시간 한도가 **30분 이상으로 완화**되는 경우
- GBDT·TabM 라인이 **완전히 정체**되고, 시도할 축이 소진된 경우 (그때도 §3 때문에 기대값은 낮음)
